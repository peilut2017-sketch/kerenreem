# מענה לפנייה ישירות מהמייל

כשפנייה חדשה מגיעה מטופס יצירת הקשר, הצוות מקבל התראה במייל. עד עכשיו
«השב» על ההתראה שלח תשובה ישירות לפונה — והיא לא הופיעה בשרשור הפנייה
במסך הניהול. מעכשיו, כשהמנגנון מופעל, תשובה במייל שקולה למענה מהניהול:

1. התשובה נשלחת לפונה מ-`contact@kerenreem.org` (באותה תבנית מותגת);
2. נשמרת בשרשור הפנייה, עם תג «נענתה במייל»;
3. הפנייה עוברת ל«בטיפול».

בנוסף, ההתראה מכילה כפתור **«מענה דרך מערכת הפניות»** שפותח את הפנייה
עצמה בניהול (`/admin/messages?open=<id>`).

## איך זה עובד

```
הצוות לוחץ «השב»
   ↓  Reply-To: contact+i<מזהה>.<חתימה>@kerenreem.org
Cloudflare Email Routing  ← כלל: contact@ → Worker
   ↓
Email Worker (cloudflare/email-worker/worker.js)
   ↓  POST /api/email/inbound  (x-inbound-secret)
האתר: אימות → ניקוי ציטוט → שליחה לפונה → שמירה בשרשור
```

* **החתימה** בכתובת (HMAC על מזהה הפנייה) היא ה-capability: רק מי שקיבל את
  ההתראה מכיר את הכתובת. מזהה שנוחש לא יעבוד.
* **השולח** חייב להיות איש צוות: משתמש ניהול בתפקיד עורך ומעלה, או אחת
  מתיבות הפניות שהוגדרו (פניות כלליות / ספרים / `SITE_NOTIFICATIONS_EMAIL`
  / כתובת יצירת הקשר). כך אפשר לענות גם מתיבה משותפת שאינה חשבון ניהול.
* **ציטוט** של ההודעה המקורית (שורת «בתאריך … כתב/ה:», `On … wrote:`,
  שורות `>`, `Original Message`) נחתך — הפונה מקבל רק מה שנכתב.
* **כפילות**: ה-Message-ID נשמר באינדקס ייחודי, ושליחה חוזרת של Cloudflare
  לא תשלח לפונה פעמיים.
* **כשל לעולם לא בולע תשובה**: אם משהו נכשל (האתר למטה, שולח לא מורשה,
  שליחה לפונה נכשלה, מייל גדול מ-4MB), ה-Worker מעביר את המייל המקורי
  לתיבת הגיבוי.
* **קבצים מצורפים** בתשובה אינם מועברים לפונה ואינם נשמרים — רק הטקסט.

## הפעלה (חד־פעמית)

הקוד מוכן. בלי ההגדרות הבאות האתר מתנהג כמו קודם (Reply-To = הפונה).

1. **מסד**: להריץ את `supabase/59_inquiry_email_replies.sql`.
2. **סוד**: ליצור ערך אקראי (`openssl rand -hex 32`) ולהגדיר באתר
   `INBOUND_EMAIL_SECRET`.
3. **Cloudflare ← Email ← Email Routing ← Settings**: להפעיל
   *Subaddressing* (כך ש-`contact+…@` מותאם לכלל של `contact@`).
4. **Worker**: Workers & Pages ← Create ← Worker, להדביק את
   `cloudflare/email-worker/worker.js`, ובהגדרות להוסיף
   `INBOUND_URL` (`https://<כתובת האתר>/api/email/inbound`),
   `INBOUND_SECRET` (Secret — אותו ערך מסעיף 2), `STAFF_INBOX`
   (תיבת הצוות) ואופציונלית `FALLBACK_TO`. שתי הכתובות חייבות להיות
   *Destination addresses* מאומתות ב-Email Routing.
5. **כלל ניתוב**: ב-Routing rules לשנות את `contact@kerenreem.org` מ-
   «Send to an email» ל-**«Send to a Worker»** ← ה-Worker מסעיף 4. דואר
   רגיל ל-`contact@` ממשיך להגיע לתיבת הצוות (ה-Worker מעביר אותו).
6. **בדיקה**: לשלוח פנייה מהטופס, ללחוץ «השב» בהתראה, ולוודא שהתשובה
   הגיעה לפונה ושהיא מופיעה בשרשור הפנייה בניהול.

## כיבוי

למחוק את `INBOUND_EMAIL_SECRET` מהסביבה: ההתראות הבאות יצאו שוב עם
Reply-To של הפונה, ונקודת הקליטה תחזיר 503. (התראות שכבר נשלחו ממשיכות
להכיל כתובת חתומה — ה-Worker יעביר את התשובות אליהן לתיבת הגיבוי.)
