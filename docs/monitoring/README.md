# ניטור ובריאות — אתר קרן רא״ם

מסמך זה מגדיר את מערכת הניטור: ארכיטקטורה, רשימת הבדיקות עם תדירויות
וספים, סכימת האירועים, ערוצי ההתראה, והקישור לספרי ההרצה (runbooks).

---

## 1. מה קרה, ומה זה מלמד

האירוע שבגללו המערכת הזו נבנתה, לפי מה שהוכח בפועל:

1. דיסק השרת התמלא.
2. הקונטיינר והאימג' של PostgreSQL היו חסרים. ה-volumes של הנתונים
   **נשמרו ולא נמחקו**.
3. בלי PostgreSQL, שירותי Supabase לא הצליחו לקרוא נתונים. הקטלוג הוצג
   זמנית כריק ודפי ספר החזירו 500.
4. אחרי שחזור אותו PostgreSQL וחיבורו לאותם volumes, המסד חזר ל-healthy.
   נמצאו 63 ספרים, מהם 62 מפורסמים ונגישים ל-anon.
5. הקטלוג חזר אחרי חלון ISR של כ-60 שניות. דפי ספר המשיכו זמנית להגיש
   500 **שנשמר במטמון** בזמן נפילת המסד, ואז התאוששו.
6. הלוגו והכריכות לא נמחקו; Storage החזיר 200. בבדיקה חיה מאוחרת הם
   הוצגו בדסקטופ ובמובייל.
7. נשארו כ-3.1GB פנויים בלבד — סיכון תפעולי.
8. **לא הוכח** מה הסיר את קונטיינר/אימג' PostgreSQL. אין לקבוע שזו הייתה
   בוודאות בעיית עומס או דיסק בלי לוגים נוספים.

### חמישה לקחים שמעצבים את כל מה שלמטה

| הלקח | מה נגזר ממנו |
|---|---|
| "עמוד הבית מחזיר 200" אינו מדד בריאות | בדיקה לכל שכבה בנפרד; בדיקה שסופרת ספרים ולא רק טוענת עמוד |
| היעדר שירות אינו מצב "unhealthy" — אין מדד בכלל | כלל `absent()` על קונטיינרים חובה, לא רק בדיקת מצב |
| תשובת 500 שנשמרה במטמון נראית כמו עמוד תקין | `Cache-Control: no-cache` בכל בדיקה; כלל נפרד ל-5xx |
| מערכת ניטור על המכונה החולה שותקת | המוניטור רץ על **מכונה נפרדת**, אצל ספק אחר אם אפשר |
| סיבת שורש לא מוכחת נשארת לא מוכחת | שמירת לוגים ואירועים; המערכת מדווחת עובדות, לא מסקנות |

## 2. ארכיטקטורה

```
                    ┌──────────────────────────────────────┐
                    │  מכונת ניטור (נפרדת, ספק/אזור אחר)   │
                    │                                      │
   בדיקות מבחוץ ←───┤  Prometheus ── Alertmanager ─┬─→ מייל │
   (HTTP/TLS/DNS)   │      ↑            ↑          ├─→ טלגרם│
                    │  Blackbox     כללי alerts    └─→ webhook
                    │                                      │  │
                    │  Uptime Kuma (לוח מצב אנושי)         │  │
                    │  cron: בדיקת דפדפן אמיתית (שעתי)     │  │
                    └───────────────┬──────────────────────┘  │
                                    │ מנהרה פרטית              │
                                    │ (WireGuard/Tailscale)    │
   ┌────────────────────────────────┴───────────────┐          │
   │  שרת האפליקציה (Hetzner + Coolify)             │          │
   │  node_exporter · cadvisor · postgres_exporter   │          │
   │  Supabase: db · rest · auth · storage · kong    │          │
   └─────────────────────────────────────────────────┘          │
                                                                │
   ┌─────────────────────────────────────────────────┐          │
   │  Vercel / Next.js                               │          │
   │  /api/health        — בדיקה רדודה, ללא אימות    │          │
   │  /api/health/deep   — בדיקה לכל שכבה, מוגנת     │          │
   │  /api/monitoring/incident  ←─────────────────────────────┘
   │        כותב ל-monitoring.incidents (ציר זמן)    │
   └─────────────────────────────────────────────────┘
```

### שלוש החלטות ארכיטקטוניות, ולמה

**המוניטור על מכונה נפרדת.** זה הסעיף החשוב ביותר במסמך. באירוע
האחרון, כל מה שרץ על השרת איבד את היכולת לדווח בדיוק כשהיה צריך. שרת
ענן קטן (2GB) אצל ספק אחר עולה כמה דולרים בחודש והוא ההבדל בין
"קיבלנו התראה" ל"לקוח התקשר".

**הסוכנים קוראים ואינם מחליטים.** על שרת האפליקציה רצים רק
`node_exporter`, `cadvisor` ו-`postgres_exporter`. אף אחד מהם אינו יכול
לעצור קונטיינר, למחוק קובץ או לכתוב למסד:
- `cadvisor` מקבל את סוקט Docker ב-**read-only**;
- `postgres_exporter` מתחבר כ-`monitoring_ro` עם `pg_monitor` בלבד —
  סטטיסטיקות, בלי קריאת נתונים ובלי כתיבה;
- אין בשום מקום `docker system prune`, ואין שום פעולת תיקון אוטומטית.

**שתי נקודות תצפית.** בדיקה שנכשלה בנקודה אחת בלבד היא כנראה רשת;
בדיקה שנכשלה בשתיהן היא האתר. `external_labels.observer` נושא את זה
אל ההתראה, ולכן אפשר להבדיל.

## 3. רשימת הבדיקות

### 3.1 שרת (node_exporter, כל 30 שניות)

| בדיקה | סף אזהרה | סף קריטי | המתנה | Runbook |
|---|---|---|---|---|
| ניצול דיסק `/` | 70% / 80% | 90% | 30ד׳ / 15ד׳ / 5ד׳ | `disk-full.md` |
| תחזית מילוי דיסק | תוך 12ש׳ | — | 30ד׳ | `disk-full.md` |
| ניצול inodes | 85% | — | 15ד׳ | `disk-full.md` |
| זיכרון פנוי | <8% | — | 15ד׳ | `server-resources.md` |
| החלפת דפים (swap) | >1000/ש׳ | — | 15ד׳ | `server-resources.md` |
| עומס מנורמל (load15/ליבות) | >2 | — | 20ד׳ | `server-resources.md` |
| סוכן מדידה לא עונה | — | `up == 0` | 5ד׳ | `server-resources.md` |

שלוש מדרגות הדיסק אינן קישוט: 70% = יש זמן, 80% = לתכנן, 90% = לפעול
עכשיו. **תחזית המילוי** (`predict_linear`) היא ההתראה היחידה שנותנת זמן
אמיתי להגיב — סף אחוזים מתריע כשכבר כמעט מאוחר.

### 3.2 Docker (cadvisor, כל 30 שניות)

| בדיקה | חומרה | המתנה |
|---|---|---|
| קונטיינר חובה **חסר** (`absent()`) | קריטי | 2ד׳ |
| קונטיינר הפסיק לדווח (נעצר) | קריטי | 2ד׳ |
| לולאת restart (>3 ברבע שעה) | קריטי | 5ד׳ |
| זיכרון קונטיינר >90% מהמגבלה | אזהרה | 15ד׳ |

הכלל הראשון הוא זה שהיה תופס את האירוע. קונטיינר שנמחק אינו מדווח
`unhealthy` — פשוט אין לו מדד. רק `absent()` תופס היעדר.

**אף כלל כאן אינו מפעיל פעולת תיקון.** המערכת מתריעה; אדם מחליט.

### 3.3 PostgreSQL (postgres_exporter, כל 30 שניות)

| בדיקה | סף | חומרה | המתנה |
|---|---|---|---|
| `pg_up` | 0 | קריטי | 1ד׳ |
| **ספרים מפורסמים** | <40 | קריטי | 5ד׳ |
| ניצול מכסת חיבורים | >80% | אזהרה | 10ד׳ |
| שאילתה פעילה ארוכה | >300ש׳ | אזהרה | 5ד׳ |
| שאילתות חסומות על נעילה | >5 | אזהרה | 5ד׳ |
| גיבוי אחרון | >36ש׳ | קריטי | 1ש׳ |

בדיקת **ספרים מפורסמים** היא לב העניין: מסד יכול להיות חי לגמרי
ובכל זאת להחזיר קטלוג ריק (RLS, שחזור חלקי, טבלה ריקה). הסף 40 נבחר
מתוך 62 בפועל — נמוך מספיק כדי שמחיקה מכוונת של כמה ספרים לא תצעק,
וגבוה מספיק כדי לתפוס קריסה.

### 3.4 Supabase (blackbox, כל 60 שניות)

כל שירות נבדק **בנפרד** — PostgREST, Auth, Storage, Kong. "Supabase
למטה" אינה אבחנה שאפשר לפעול לפיה.

שערי Supabase מחזירים 401 ללא מפתח, וזו תשובה **תקינה** שאומרת
שהשירות חי; המודול `http_401_ok` מקבל אותה. מודול שמצפה ל-200 כאן היה
אדום תמיד — ואחרי יומיים אף אחד לא מסתכל עליו.

בנוסף, `/api/health/deep` מבצע כל שתי דקות **GET אמיתי עם anon**
שסופר רשומות, ומוריד **קובץ עוגן מ-Storage** ובודק את סוגו וגודלו.

### 3.5 עמודי משתמש (blackbox, כל 60 שניות)

`/`, `/books`, `/authors`, `/activities`, `/events`, `/contact`, `/en`,
ועמוד ספר ידוע בעברית ובאנגלית.

לכל עמוד נבדקים: קוד תשובה, זמן תגובה, טקסט צפוי בגוף, והיעדר טקסט
שגיאה. הבדיקות נשלחות עם `Cache-Control: no-cache` — **בדיקה שמקבלת
תשובה שמורה אינה בדיקה**, וזו בדיוק הסיבה ש-500 שמור נראה תקין.

| בדיקה | חומרה | המתנה |
|---|---|---|
| עמוד לא נטען | קריטי | 2ד׳ |
| עמוד מחזיר 5xx | קריטי | 2ד׳ |
| `/api/health/deep` מחזיר 503 | קריטי | 3ד׳ |
| זמן טעינה ממוצע >3ש׳ | אזהרה | 15ד׳ |

### 3.6 נכסים ודפדפן אמיתי

- **כל 5 דקות (blackbox):** שני הלוגואים, הרקע, וכריכות עוגן.
- **כל שעה (Playwright):** `monitoring/scripts/synthetic-browser.mjs` —
  דסקטופ ומובייל, גולל עד התחתית ומוודא ש**כל תמונה גלויה באמת נטענה**
  (`naturalWidth > 0`). זו הבדיקה שתופסת קובץ שנעלם מ-Storage: ה-HTML
  תקין, תג ה-`img` קיים, והתמונה לא שם. היא גם תופסת שגיאות JavaScript,
  בקשות רשת שנכשלו, וגלישה אופקית במובייל.

### 3.7 רשת, DNS ו-TLS

| בדיקה | תדירות | סף |
|---|---|---|
| תרגום DNS | 5ד׳ | כשל → קריטי אחרי 5ד׳ |
| תוקף תעודת TLS | 5ד׳ | <14 יום אזהרה, <5 ימים קריטי |
| ICMP לשרת | 60ש׳ | מבדיל "השרת למטה" מ"האפליקציה למטה" |

### 3.8 Vercel / Next.js

`/api/health` מחזיר `build` (SHA), `environment`, `uptimeSeconds`
ו-`canonicalUrl`. כך אפשר לזהות פריסה חדשה, מופע שרק עלה (שמסביר
השהיה חריגה בלי להזעיק אף אחד), ו**סטייה בכתובת הקנונית** — הבאג
שבגללו sitemap.xml פרסם `kerenreem.vercel.app`.

`scripts/check-canonical.mjs` רץ אחרי כל פריסה ופעם ביום, ובודק
sitemap, robots, canonical, hreflang ו-og:url בכל עמודי המפתח.

## 4. סכימת האירועים

`supabase/56_monitoring.sql` — סכימה **חדשה ונפרדת** (`monitoring`).
אינה נוגעת בשום טבלה קיימת, אינה משנה מדיניות קיימת, ואינה מוחקת דבר.

| טבלה | תפקיד | שמירה |
|---|---|---|
| `monitoring.incidents` | אירוע אחד = תקלה אחת, מהתסמין ועד ההתאוששות | שנה |
| `monitoring.incident_events` | ציר הזמן: כל תסמין, מצב ופעולה | עם האירוע |
| `monitoring.check_samples` | תוצאות בדיקה גולמיות, כולל התקינות | 14 יום |

השדה `dedupe_key` (`{scope}:{component}`) + אינדקס ייחודי חלקי על
אירועים שאינם `resolved` הם מה שמבטיח **אירוע אחד עם עשרה תסמינים**
במקום עשר התראות.

שמירת דגימות תקינות נחוצה כדי לענות על "מתי זה התחיל להידרדר": זמן
תגובה שזוחל מ-200ms ל-1.5s במשך שבוע אינו כשל באף רגע בודד, והוא
האזהרה האמיתית. `monitoring.prune()` מריץ טיהור — מערכת ניטור שממלאת
את הדיסק היא אירוניה יקרה.

## 5. ערוצי התראה

| חומרה | ערוצים | המתנה ראשונה | חזרה |
|---|---|---|---|
| קריטי | מייל + טלגרם + webhook לאירועים | 10ש׳ | שעה |
| אזהרה | מייל + webhook | 30ש׳ | 4 שעות |

מייל לבדו אינו מעיר אף אחד בשתיים בלילה, וזו בדיוק השעה שבה דיסק
מתמלא — ולכן קריטי יוצא בשני ערוצים.

**קיבוץ:** `group_by: [scope]`. נפילת PostgreSQL הייתה מייצרת בקלות
עשר התראות (מסד, PostgREST, קטלוג ריק, דף ספר 500, בדיקת בריאות,
עמוד איטי…). עשר הודעות על תקלה אחת הן רעש שמסתיר את השאלה היחידה
שחשובה.

**השתקות נגזרות** (`inhibit_rules`) משקפות את שרשרת התלות האמיתית:

```
דיסק מלא → PostgreSQL נופל → PostgREST שוגה → קטלוג ריק → דף ספר 500
```

כשהשורש ידוע, הענפים מושתקים. בלי זה, אף אחת מעשר ההתראות לא אומרת
"הדיסק התמלא".

**הודעת התאוששות** נשלחת תמיד (`send_resolved: true`) — תקלה שנסגרה
בלי הודעה משאירה את כולם בדריכות.

**מצב תחזוקה:** לפני פריסה מתוכננת —
`amtool silence add maintenance=true --duration=30m`. פריסה שמייצרת
חמש התראות "העמוד לא נטען" מאמנת את הצוות להתעלם מהן.

## 6. לוח האירועים — איפה מסתכלים

**בניהול: מערכת ← בריאות המערכת** (`/admin/monitoring`). זה המסך
שעונה על "מה קורה עכשיו, ומה קרה", בלי להתחבר לשרת ובלי לשלוף אסימון.

שני חלקים:

- **מצב עכשיו** — הבדיקות רצות בזמן טעינת המסך, מול המסד והאחסון
  ממש: מסד נתונים, ספירת הקטלוג, הורדת קובץ עוגן, הכתובת הקנונית,
  ספק הדואר, וקליטת ההתראות. אותן בדיקות בדיוק כמו
  `/api/health/deep`, כדי ששני המקומות לא יוכלו לחלוק על עצמם.
  המסך הוא `force-dynamic` ואינו מוגש ממטמון — מסך בריאות ששמור
  במטמון הוא בדיוק הכישלון שהמערכת נבנתה כדי למנוע.
- **אירועים** — כל אירוע עם ציר זמן, השירות שנפל, ההשפעה בשפה
  אנושית, משך, `build SHA`, מדדי השרת ברגע האירוע וקישורים ללוגים
  (`generatorURL`). אפשר לסמן "בטיפול" או לסגור ידנית.

המסך **אינו** מציע שום פעולת תיקון אוטומטית — לא הפעלה מחדש של
שירות ולא נגיעה בקונטיינרים. זו החלטה מפורשת: מערכת שמתקנת בעצמה
היא מערכת שיכולה גם להזיק בעצמה. הפעולה היחידה שכן קיימת שם היא
רענון המטמון הציבורי, שסוגרת את המקרה של "התשתית חזרה אבל העמוד
עדיין מציג שגיאה שנשמרה".

**מחוץ לניהול:**

| מה | איפה |
|---|---|
| מדדי שרת, דיסק, קונטיינרים, PostgreSQL | Prometheus / Uptime Kuma, על מכונת הניטור הנפרדת |
| בדיקה חיצונית בפורמט JSON | `/api/health` (פתוחה), `/api/health/deep` (מוגנת בסוד) |
| התראות | מייל + טלגרם, ראו סעיף 5 |

`/api/monitoring/incident` קולט את ה-webhook מ-Alertmanager וכותב דרך
`monitoring.raise_incident` / `monitoring.resolve_incident`. המסך קורא
דרך `admin_list_incidents` / `admin_incident_timeline` — פונקציות
`security definer` גדורות ב-`is_admin()`, כי הסכימה `monitoring` סגורה
לחלוטין ל-`anon` ול-`authenticated`.

### הכללים שחוצים את כל ה-runbooks

1. **לעולם לא למחוק volume של מסד נתונים.** לא ידנית, ולא דרך
   `docker system prune --volumes`. ה-volumes הם מה שהציל את הנתונים
   באירוע האחרון.
2. **לא לאפס pending settings ב-Coolify.**
3. **Snapshot לפני כל שינוי מסוכן.**
4. **לא לפרוס SHA אחר בלי אישור.**
5. **Snapshot אינו תחליף לגיבוי מסד.**

## 8. התקנה

### 8.1 מכונת הניטור

```bash
scp -r monitoring/ monitor-host:/opt/kerenreem-monitoring
ssh monitor-host
cd /opt/kerenreem-monitoring
cp .env.example .env && $EDITOR .env
# להחליף בקבצים: APP_HOST, SUPABASE_HOST, CANARY_BOOK_SLUG,
# CANARY_EXPECTED_TEXT, HEALTH_CHECK_SECRET_PLACEHOLDER
docker compose up -d
```

### 8.2 סוכנים על שרת האפליקציה

```sql
-- פעם אחת, במסד:
create user monitoring_ro with password '…';
grant pg_monitor to monitoring_ro;
```

```bash
docker compose -f docker-compose.agents.yml up -d
```

הפורטים נקשרים ל-`127.0.0.1` בלבד. הגישה של מכונת הניטור אליהם היא
דרך מנהרה פרטית ולא דרך האינטרנט — מדדי שרת חשופים הם מפת דרכים לתוקף.

### 8.3 באפליקציה

הרצת `supabase/56_monitoring.sql`, והוספת משתני הסביבה:

```
HEALTH_CHECK_SECRET=          # סוד לבדיקה העמוקה (נפרד מ-CRON_SECRET)
HEALTH_MIN_PUBLISHED_BOOKS=40 # סף הקטלוג
HEALTH_STORAGE_CANARY=covers/<קובץ קיים>.jpg
INCIDENT_WEBHOOK_SECRET=      # סוד ל-webhook האירועים
NEXT_PUBLIC_SITE_URL=https://www.kerenreem.org
```

### 8.4 בדיקת דפדפן שעתית

```cron
17 * * * * cd /opt/kerenreem-monitoring && node scripts/synthetic-browser.mjs \
  --base https://www.kerenreem.org --book <slug> >> /var/log/kr-browser.log 2>&1
```

דקה 17 ולא 0: שעה עגולה היא הדקה העמוסה ביותר בכל מערכת מתוזמנת.

## 9. שדרוג השרת

3.1GB פנויים הם סיכון תפעולי, ומערכת הניטור מקטינה את הסיכון אבל אינה
מסירה אותו. עד השדרוג, `DiskWillFillSoon` היא ההתראה החשובה ביותר
במערכת — היא זו שנותנת שעות להגיב במקום דקות.
